# 学生端重构设计:从「透明浮层」到「窗口化课堂客户端」

> 结论:现在这套「全屏透明浮层 + 只同步白板笔迹」的学生端,确实撑不住真实课堂。
> 学生端应该改成**普通可调窗口的会议式客户端**:中间是老师共享的屏幕(PPT/桌面/白板),
> 上面是课堂状态栏,下面是课堂控制条,右侧是可折叠的成员/聊天/互动面板。
> 教师端继续保留现有悬浮层逻辑(这套逻辑是对的)。

## 一、C30 学生端参考(实际查到的)

C30 是沐坤科技的智能教学系统,学生端以 **iOS / iPad / Android** 为主(Windows 上官方只提供
教师端/备课端,没有原生 PC 学生端),所以「PC 窗口化」是我们在它的移动端形态上做的桌面适配。

- [C30 学生端 App Store](https://apps.apple.com/cn/app/c30%E5%AD%A6%E7%94%9F%E7%AB%AF/id1469687292)
- [C30 在线帮助文档 · 传屏](http://px.iclass30.com/help/stu_app/help-doc/%e4%bc%a0%e5%b1%8f/%e4%bc%a0%e5%b1%8f.html)
- [C30 客户端下载](https://px.iclass30.com/download/)
- [C30 智能教学系统使用手册(PDF)](https://file.icve.com.cn/ssykt/362/322/5AB50A569F93573CEB0A81356E554628.pdf)

从 App Store 截图/帮助文档可以确认:

1. **课堂主画面就是老师的屏幕**,不是白板替代品。帮助文档写得很明确:
   「教师在大屏端点击**共享屏幕**,将大屏端屏幕画面**实时共享至学生端**」;
   另外还有「**截屏发送**」「投屏讲解」。
2. 学生端课堂页的结构是:
   - 顶栏:学生名 / **授课老师** / 班级名 / 网络状态 / **退出课堂**;
   - 中间:老师的桌面(Windows 桌面、Word、PPT 等)整屏显示;
   - 左右/右侧:可收起的工具导轨(下屏、白板、课本、操作、窗口、退出等);
   - 底部:颜色/截图/提醒/撤销/收起等小工具条;
   - 互动浮层:**抢答**大按钮、答题、讨论、弹幕等。
3. iPad 横屏截图里还能看到「抢答」「查看题面」覆盖在老师屏幕上方 —— 说明**屏幕广播是底图,
   互动/批注是叠加层**。
4. C30 学生端在课堂里基本是「全屏观看 + 轻量工具」;我们做桌面窗口化时,
   把它收敛成会议软件的三段式(顶栏 / 舞台 / 底栏 + 右侧抽屉)即可。

- 默认窗口 1280×800,可缩放/最大化,最小 960×600;记住上次窗口位置。
- 舞台永远保持老师画面的宽高比(16:9 / 老师屏幕比例),黑边留白。
- 顶栏显示课堂状态和计时;「共享屏幕 / 白板」由老师端决定,学生只显示当前模式。
- 底栏是课堂级操作,不做画笔(学生不往老师屏幕上画);后续可加「笔记 / 截图」。
- 右侧抽屉:成员、聊天、互动(答题/抢答/举手/投票等),默认收起,不挤压舞台。

## 三、核心架构

### 1. 主进程:普通窗口

`apps/student/src/main/index.ts` 从「全屏透明 + 鼠标穿透」改为:

```
BrowserWindow {
  width: 1280, height: 800, minWidth: 960, minHeight: 600,
  frame: true, transparent: false, backgroundColor: '#0f1115',
  show: false, resizable: true, maximizable: true,
}
```

- 删除 `setIgnoreMouseEvents` / `transparent` / 全屏 `bounds` 逻辑;
- 保留单例锁、mDNS 发现;窗口关闭 = 退出(在上课中时弹二次确认);
- 可选「始终置顶」开关(会议软件的常见能力),默认关闭;
- 记住窗口 bounds(userData 下 JSON 即可,不引新依赖);
- 这样也天然适配 arm64(学生端没有原生模块)。

### 2. 舞台与坐标系(最容易踩坑)

现在学生端画布直接用老师端坐标画,窗口/分辨率不一致就会错位。窗口化后必须先定义:

- **虚拟画布**:老师主显示器的逻辑尺寸,例如 `board = { w: 2560, h: 1440 }`;
- 所有 `Stroke` / `ImageItem` 坐标都以这块虚拟画布为准(教师端现有坐标本来就是屏幕坐标);
- 学生端舞台按 `scale = min(stageW / board.w, stageH / board.h)` 等比缩放 + 居中,
  再统一套一层 `translate(offset) scale(scale)`;
- 屏幕帧、白板、图片、老师光标全部走同一个变换,保证「笔迹正好压在 PPT 上」;
- 老师端在建课 / 上课状态里带上 `board` 尺寸,学生端按它渲染。

> 这一条不改,窗口化以后所有笔迹都会偏;比换 UI 更优先。

### 3. 老师端:屏幕共享管线

- 采集:`desktopCapturer` 主屏 → `nativeImage` → 缩放到 1280×720 左右 → JPEG q≈0.6;
- 节流:**内容有变化才发**,目标 1–2 fps;PPT 翻页足够,静态页面几乎不占带宽;
- 老师悬浮层要**从采集里排除**,否则学生看到侧边栏/工具栏,还会和笔迹重影:
  - Windows 10 2004+ 用 `win.setContentProtection(true)`(`WDA_EXCLUDEFROMCAPTURE`);
  - 这条需要在真机验证:排除后 `desktopCapturer` 是否还能拿到干净桌面。
- 光标单独发:`cursor.move {x,y}` 15–20 Hz,学生端画一个小光标,比把光标烧进低帧率画面顺畅;
- 笔迹继续走现有 `whiteboard.event` 实时通道,学生端叠加在屏幕帧上;
- 老师端增加「共享屏幕 / 白板」切换:
  - 白板模式:白底 + 笔迹(现有逻辑,不传屏幕帧);
  - 投屏模式:屏幕帧 + 笔迹 + 光标;
  - 截屏发送:把一张图作为 `image` 推到舞台,学生端按图片模式显示。

### 4. 协议(在现有 socket.io 上扩展)

```ts
// 课堂/舞台状态
stage.state {
  roomCode: string;
  mode: 'screen' | 'whiteboard' | 'image';
  board: { w: number; h: number };     // 老师虚拟画布
  screen?: { w: number; h: number };   // 采集源逻辑尺寸
  image?: { src: string; w: number; h: number };
}

// 屏幕帧(二进制,走 socket.io binary)
screen.frame(buffer: ArrayBuffer, meta: { seq, ts, w, h })

// 老师光标
cursor.move { roomCode, x, y }

// 复用现有
whiteboard.event / whiteboard.state / session.* / class.state
```

- 帧只在 `class.state.active === true` 且 `stage.mode === 'screen'` 时发送;
- 下课后停帧;重新上课发 keyframe;
- 学生中途进入:先 `stage.state`,再请求一帧 keyframe。

### 5. 传输方案取舍

| 方案 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **帧推送(推荐先做)** | 复用 socket.io,无信令/SFU,ARM64 无压力;PPT 静态内容足够 | 视频/动画卡;30 人时上行带宽要控制 | 当前 Demo、PPT/桌面/板书 |
| WebRTC(mesh) | 流畅、低延迟 | 每个学生一条连接,老师上行 ×N;30 人不可行 | 小班 1–4 人 |
| WebRTC + 本地 SFU | 大班可行、可扩展 | 引入 mediasoup 等重组件,构建/部署复杂 | 后续产品化 |

建议:**先用帧推送把「共享屏幕 + 笔迹叠加 + 窗口化」跑通**,把传输层抽象成
`ScreenTransport` 接口,后续换 WebRTC/SFU 不动 UI。

## 四、分阶段落地

### P0 坐标系与协议(1 个改动单元)
- `stage.state` / `board` 尺寸;学生端把现有白板渲染改成「等比适配舞台」;
- 验收:老师 2560×1440、学生 1280×800,笔迹仍压在正确位置。

### P1 窗口化壳(可独立验收)
- 主进程普通窗口;删除透明/穿透;
- 加入课堂页、等待页、上课页三段式;顶栏/底栏/右侧抽屉;
- 白板模式在舞台里显示(先不接屏幕共享);
- 验收:窗口可缩放/最大化;等待→上课→下课状态正确;白板内容缩放正确。

### P2 屏幕共享(核心)
- 老师端采集/节流/排除悬浮层;学生端 canvas 渲染帧 + 光标 + 笔迹;
- 老师端「投屏 / 白板」切换;
- 验收:老师打开 PPT 翻页,学生窗口内 1–2s 内看到;笔迹对齐;带宽/CPU 可接受。

### P3 课堂能力补齐
- 成员/聊天/互动抽屉接入现有 `interact.*` 协议;
- 举手/抢答/答题浮层;截图发送;全屏;始终置顶;断线重连;
- 验收:一节课完整走通(进房→等待→上课→投屏→互动→下课→退出)。

## 五、风险与取舍

1. **窗口化会丢掉「始终盖在桌面上」**:学生可能切到别的窗口。用「始终置顶」开关兜底,
   默认关闭;老师端仍保持悬浮层。
2. **带宽**:帧推送在 30 人班级要限分辨率/帧率;先按 1280×720、1–2 fps、变化才发,
   实测后再调。视频教学场景再上 WebRTC。
3. **DPI/缩放**:老师端 150%/200% 缩放下,逻辑坐标与物理像素要分开记录;统一用逻辑坐标传输,
   采集帧带物理尺寸,学生端只做等比缩放。
4. **采集排除悬浮层**:`setContentProtection` 的行为需在 Windows 10/11 真机验证;
   如果拿不到干净画面,退路是采集时短暂隐藏悬浮层(会有闪烁,不优先)。
5. **并发改动**:「课堂互动」模块已落地(见 [interact-design.md](interact-design.md),`InteractSnapshot` / `interact.*`
   协议、`InteractionControl.interactEnabled` 已稳定);学生端窗口化重构直接复用这套协议,不要再起第二套互动状态。

## 七、实施记录(2026-11-19)

按「WebRTC 一步到位 + P1 窗口壳 + P2 投屏 + 系统原生边框」落地:

- **P1**:学生端主进程改为普通窗口(原生边框、可缩放/最大化),UI 为「我的课堂 → 等待页 → 上课页」三段式;
  顶栏 = 老师/上课计时/在线学生数/全屏/退出,舞台 = 老师画面,底栏 = 跟随模式与连接状态。
- **P2**:老师端 `getDisplayMedia` + 每学生一路 `RTCPeerConnection`;信令走现有 socket.io;
  `setContentProtection` 把悬浮层排除出采集;学生端按 `board` 等比缩放视频、白板和笔迹;
  老师光标 20Hz 单独广播;白板/投屏由老师是否在白板自动切换。
- **协议**:`stage.state` / `stage.set` / `cursor.move` / `rtc.request|offer|answer|ice|stop|peer-left`;
  服务端只转发并做上课态门控。
- **验证**:真实双端 CDP 跑通「加入 → 上课 → 投屏 → 白板 → 回投屏 → 下课 → 再上课」;
  视频 1920×1080、画面为老师桌面且不含悬浮层;注入笔迹按 board 缩放位置正确;
  teacher/student `tsc --noEmit` 与构建通过。
- **暂未做**:副屏选择、聚焦层同步、30 人 SFU、学生截图/笔记、成员/聊天抽屉(P3)。
