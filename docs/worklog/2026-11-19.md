## 「窗口」面板第二轮:统一成深色浮层 + 只列任务栏窗口(2026-11-19 凌晨)

- **用户反馈(两条)**:①窗口面板是白底,和其他浮层(侧边栏/菜单/画笔面板)的黑色系不一致;②列出来的窗口太多,
  只要任务栏里有的那些。
- **① 深色化(`FloatingDock.tsx` 窗口面板)**:
  - 面板底 `rgba(27,27,31,0.96)` + 边框 `#3a3a40` + 圆角/阴影对齐侧边栏与菜单浮层;标题白字,关闭叉号 hover 变亮;

- **② 只列任务栏窗口(`main/index.ts` `enumerateAllWindows` 换成任务栏规则)**:
  - 原有的「可见 + 有标题」之外,按 Windows 任务栏的显示条件过滤:
    - `WS_EX_TOOLWINDOW` 的工具窗口不列(命令面板、PowerToys Quick Access、QQ音乐精简模式、RzMonitor 等);
    - 有 owner(`GetWindow(h, GW_OWNER)`)的辅助窗口不列;

      (桌面、任务栏本身、UWP 内容窗口——它的 `ApplicationFrameWindow` 外壳才是任务栏按钮);
    - `WS_EX_APPWINDOW` 优先:应用主动要求上任务栏时即使 owned/toolwindow 也列(Fork 就是这种)。
  - P/Invoke 增加 `GetClassName` / `GetWindowLong` / `GetWindow` / `DwmGetWindowAttribute(dwmapi.dll)`。
- **实测(本机,过滤前后对比)**:
  - 过滤前 16 条:`设置`×2、`Windows 输入体验`、`Program Manager`、`命令面板`、`PowerToys Quick Access`、
    `精简模式-QQ音乐`、`RzMonitorForegroundWindow` 等一堆不该上任务栏的;

## 课堂互动落地:互动菜单从「空着」到六种真实互动(2026-11-19 凌晨)

- **用户需求**:「上网找一下 C30 智能教学软件的互动有哪些,做一些基础功能丰富一下,就这个菜单空着了;
  学生端必须对应有功能,不能是 demo」。
- **调研**(C30 教育云 / 学生端 App Store / 使用手册):互动板块 = 随机点名、抢答、举手、实时投票、
  观点云、计时、互动答题(限时练)、扫码传图、投屏讲解、锁屏。本版先做**不依赖题库/文件/屏幕采集**的六种:
  随机点名 / 抢答 / 举手 / 投票 / 观点云 / 计时;答题、扫码传图、分组投屏列为后续。详见 `docs/interact-design.md`。
- **交互**:
  - 教师端底部「互动」不再切换绘制工具,而是展开/收起一块深色互动面板(与画笔/板擦浮层同一套视觉);
    功能菜单 3×2 卡片 → 配置页(题目/选项/限时)→ 发起后自动切结果页;
  - 结果页:投票实时柱状图(票数/占比/已投/未投)、抢答名次(第 1 名高亮)、观点云(同词合并、按热度放大)、
    点名姓名 + 已确认状态、计时大号倒计时;结束后保留结果,「关闭结果」才清空;

    抢答 → 大按钮 + 倒计时 + 第 N 名;投票 → 题目/选项卡片(可改票,实时票数);观点云 → 输入 ≤30 字、可改;

  点名只抽在线学生、多人时避开上次;学生掉线移出举手;`class.end` 清空互动;关闭总开关立即清空。

## 人数口径统一(教师端 1 / 学生端 2 错位)(2026-11-19 凌晨)

- **现象**:同一间教室只有 1 个学生时,教师端右上角「班级 1 人」,学生端顶栏「2 人」。
- **根因**:两端各算一份 —— 教师端 `members.filter(role==='STUDENT').length`(只算学生);
  学生端窗口化改版后顶栏用 `studentCount + 1`、等待页用 `members.length`(把老师也算进去)。
- **修复**:`packages/shared/session.ts` 新增 `countStudents(members)` 作为唯一口径(在线学生数,不含教师);
  教师端 `TeacherWorkspace`、学生端 `StudentWorkspace` 都改用它;学生端顶栏「学生 N」、
  等待页「N 名学生在课堂」、白板提示「N 名同学在线」;课堂成员列表仍显示全部成员(含老师),两者语义分开。
- **误操作回滚**:为标清楚口径,曾把教师端状态条的「班级」标签改成「学生」,看起来像「房间名变成了学生」;
  已改回「班级 N 人」——那个位置是班级/教室信息,不是人数标签。
- **验证**(真机双端,学生端 1899×1145 窗口):教师端「局域网 班级 1 人」,学生端「局域网 学生 1」,
  上课中状态一致;截图 `17-teacher-count.png` / `17-student-count.png`(临时目录)。
- **踩坑**:学生端 dev 进程一度仍在跑旧代码(顶栏显示 3),`Page.reload({ignoreCache:true})` 后依旧;
  直接 `Invoke-WebRequest http://localhost:5174/src/components/StudentWorkspace.tsx` 发现 Vite 仍返回旧转换结果 ——
  DSH 写文件是原子替换,chokidar 偶尔收不到变更事件。`LastWriteTime` 触碰文件后 Vite 重新转换、HMR 生效。
  结论:改完源码后如果 UI 还是旧的,先确认 dev server 返回的模块内容,而不是怀疑逻辑。

## 学生端窗口化 + WebRTC 屏幕共享(P1+P2,2026-11-19 凌晨)

- **用户决策**:不再只接收白板,老师要能投屏放 PPT;学生端改成会议软件式窗口应用(原生边框)。
- **主进程(学生端)**:全屏透明悬浮层 → 普通 `BrowserWindow` 1280×800、最小 960×600、可缩放/最大化/全屏;
  删除 `setIgnoreMouseEvents` / 透明 / 固定 bounds;保留单例锁,第二次启动恢复并聚焦。
  实测窗口样式 `WS_CAPTION | WS_THICKFRAME`。
- **学生端 UI 三段式**:我的课堂(房间列表)→ 等待页 → 上课页(顶栏:老师/上课计时/人数/全屏/退出;
  舞台:老师屏幕或白板;底栏:当前跟随模式)。等待页在老师未上课/已下课/断线时显示,断线文案为「课堂连接已断开」。
- **屏幕共享(WebRTC)**:
  - 老师端 `useScreenShare`:渲染层 `getDisplayMedia` + 主进程 `setDisplayMediaRequestHandler` 自动选主屏;
    每个学生一路 `RTCPeerConnection`(`iceServers: []`,局域网 host candidate),学生 `rtc.request` → 老师 offer →
    学生 answer;信令由内嵌 socket.io 服务端按 socket.id 转发,全部要求 `class.state.active`。
  - **采集排除悬浮层**:共享期间主进程 `setContentProtection(true)`(WDA_EXCLUDEFROMCAPTURE),
    学生画面里没有侧边栏/工具栏;停止共享恢复。实测开/关内容保护时,学生视频里侧边栏和底部工具条的出现/消失可复现。
  - 老师光标 20Hz 单独广播,学生端叠加橙色圆点;笔迹继续走 `whiteboard.event`,在视频上透明叠加。
  - 老师「白板 / 投屏」由 `active==='whiteboard'` 自动决定:打开白板广播 `stage.set whiteboard`,
    关闭广播 `screen`;重连/`session.joined` 时重发一次当前舞台,避免服务端停在旧模式。
- **坐标系**:老师端 `stage.set/class.start` 带上 `board = {w:innerWidth,h:innerHeight}`(主显示器逻辑尺寸);
  学生端 `ClassStage` 按 `min(stageW/board.w, stageH/board.h)` 等比缩放 + 居中,视频 `objectFit:cover`(裁掉任务栏)。

  4. 学生端截图/笔记、成员/聊天抽屉、举手/答题抽屉仍属 P3;当前互动浮层沿用已有 `StudentInteract`。
  5. 老师光标同时可能被采进视频(Chromium 默认包含鼠标),学生端再叠一个跟手圆点;如嫌重影,后续在采集约束里关光标。


## 学生端房间列表堆出 4 个「王老师的课堂」(2026-11-19 凌晨)

- **现象**:学生端「我的课堂」同时列出 4 个同名房间(ZW8YXM / HSZQ2X / WCU8XY / JQFKY4),点进去有的永远黑屏。
- **根因(两条叠加)**:
  1. 教师端 `App.tsx` 的匿名 teacherId 是 `Math.random()`,**每次渲染层重载都会变**;服务端按 teacherId
     复用课堂,id 一变就新建一间教室,老教室继续留在内存里(老师成员常驻、仍可 join)。开发期 HMR
     几次就攒出 4 间。
  2. 学生端只处理 mDNS 的 found,**不处理 down/过期**,也不校验房间是否还活着;`discoveredRooms`
     Map 和渲染列表都只增不减,于是 4 张卡片一直挂着。
- **修复**:
  - `App.tsx`:teacherId 持久化到 `localStorage('c30.teacher.identity')`,只有首次启动生成;
  - `localSessionServer`:`closeOtherRooms()` —— 同一内嵌服务器只服务一间课堂,新建/复用课堂时把
    遗留房间发 `session.error` 并删除(含 socketIndex / teacherRooms / 定时器);
  - `localSessionServer`:`discovery.probe` —— 学生端列表探活,按 `teacherLastSeenAt`(断开后 10s 宽限)
    只回「老师在线」的 roomCode;
  - `mdsd`:`subscribe(onFound, onLost)`,监听 Browser 的 `down`(goodbye/过期),
    Student main 删 Map 并推 `discovery:lost`,渲染层移除卡片;
  - `StudentWorkspace`:列表变化时按 host:port 探活,剔除非 live 房间;`session.error`(不存在/已重建)
    与 `connect_error` 时把对应卡片从列表摘掉。
- **验证**(真机:教师端 F4N28D + 学生端):
  - 冷启动只发现 1 个房间;教师端 `Page.reload` 后房间号仍是 F4N28D(identity 稳定,不再新建);
  - 临时用 bonjour-service 发一个假房间 `c30-FAKE01`:学生主进程 `discovery.getRooms()` 能看到 2 条,
    但渲染列表只剩 F4N28D —— 探活把「服务端不认识的房间」滤掉了;
  - 假房间停播(goodbye)后,主进程房间 Map 也回到 1 条 —— `down` 链路通;
  - 加入后人数一致:学生「1 名学生在课堂」、教师「班级 1 人」。
- **备注**:`closeOtherRooms` 会关闭同进程里的旧房间,所以教师端以后热更新/刷新不会再产生幽灵课堂;
  如果旧版本已经把房间堆住了,重启一次教师端即可清空(本次已重启验证)。
