## 聚焦(关灯)功能五项修复(2026-11-18 凌晨)
- **用户反馈五项问题**:①聚焦菜单(关灯/放大/插入白板/保存/关闭)固定在底部居中,应跟随矩形框;②关灯默认高亮(不该);③点关灯无效果;④"放大"应是矩形框内内容放大(像放大镜),不是放大框本身;⑤保存点击无效。
- **根因与修复(SpotlightLayer.tsx 重构)**:
  1. **菜单跟随框**:菜单从 `position:fixed bottom:90 left:50%` 改为 `position:absolute`,坐标按 rect 计算——优先放框下方(rect.y+rect.h+GAP),空间不足放框上方;水平居中于框(menuLeft 钳制屏幕边界)。
  2. **关灯默认不高亮**:状态从 `zoomed:boolean` 改为 `mode:'off'|'magnify'`(默认 off)。关灯按钮**不设 active**(默认态不高亮);放大按钮 `active={mode==='magnify'}` 仅在放大镜模式高亮。
  3. **关灯点击有效**:关灯按钮 `setMode('off')+setMagnifyImage(null)`,从放大镜切回关灯态(遮罩挖孔透出桌面)。
  4. **放大=放大镜**:新增 `onCapture(rect)` prop。点击放大→`enterMagnify` 截取当前框内容(desktopCapturer)→框内叠加 `overflow:hidden` 容器 + `<img>` 用 `transform:scale(2) + transformOrigin:center` 放大显示(中心内容放大、边缘裁切),矩形框本身不动。框移动/缩放松手时(`onPointerUp`)在 magnify 模式重新截屏刷新。
  5. **保存无效**:两处根因——(a)`dialog.showSaveDialog(mainWindow!)` 把 `focusable:false + type:'toolbar'` 的悬浮窗口作 parent,模态对话框无法弹出;改为**不传 parent**。(b)截屏会把悬浮窗口自己的遮罩/挖孔框/蓝框/手柄一并截入,导致"插入白板/保存/放大"截到脏画面。
- **主进程 index.ts 修复**:
  - `captureScreenRect`:截屏前 `mainWindow.hide()` + 等 120ms(DWM 移除窗口画面)→ 截屏 → `finally` 里 `showInactive()+setFocusable(false)` 恢复(不抢前台焦点)。所有截屏(insert/save/magnify)均获干净桌面内容。
  - `spotlight:save` 的 `dialog.showSaveDialog` 去掉 parent 参数。
- **TeacherWorkspace**:SpotlightLayer 传 `onCapture={(rect)=>api.spotlight.capture(rect)}`。
- **技术要点**:框 div 不设 overflow:hidden(否则裁掉 -5px 手柄),放大图容器单独 overflow:hidden;`rectRef` 始终同步最新 rect 供指针事件闭包读取(避免 setState 闭包过期);放大截屏用 `capturingRef` 防抖。
- 验证:teacher tsc 全净(0 错)。

## 修复:聚焦「保存 → 取消」后浮层不响应点击(2026-11-18)
- **用户反馈**:聚焦模式下点「保存」,在原生「另存为」对话框点「取消」,回到桌面后浮层/工具栏完全点不动。
- **复现链路**:聚焦(locked=true → 交互态)→ 点保存 → `setActiveTool('select')` 退出聚焦层 → 主进程 `hide()` 窗口 + 弹原生对话框 → 取消 → `restoreFloatingWindow()` 显示窗口。
- **根因一(渲染层穿透状态失同步,已确定存在)**:`usePointerPassthrough` 里「锁定切换」和「hover 检测」各存一份缓存——hover 用 effect 内的 `lastState` 闭包变量,锁定切换却直接调 `setInteractive(locked)` 不改缓存。于是退出聚焦时主进程被切成穿透态,渲染层 `lastState` 仍是 true;鼠标再移到浮层上时 `apply(true)` 被判为「与缓存相同」而**跳过上报**,主进程永远停在穿透态 → 点不动。
- **根因二(forward 转发可能静默失效)**:`setIgnoreMouseEvents(true,{forward:true})` 的 mousemove 转发在窗口 hide→show、GPU 进程重建后会静默失效(不报错只是不转发)。此时渲染层收不到任何 mousemove,hover 检测不触发;且原生对话框关闭后鼠标停在按钮上不动,也不会有事件把它「唤醒」。
- **修复(3 个文件)**:
  1. `usePointerPassthrough.ts`:**穿透状态只留一份真源**(`lastStateRef`),锁定切换与 hover 共用同一 `apply`;退出锁定时不再盲发 `false`,而是用最近鼠标位置 + `document.elementFromPoint` 重新判定(避免鼠标恰好停在工具栏上被锁死成穿透态);新增主进程鼠标位置订阅(兜底)。
  2. `main/index.ts`:新增 `syncCursorToRenderer()`(屏幕坐标→渲染层 CSS 像素)、`startCursorSyncFallback()`(仅穿透态下 60ms 轮询、位置变化才发)、`reapplyPassthrough()`(窗口重新显示时用渲染层上报值重挂 `setIgnoreMouseEvents` + 立即推一次鼠标位置);在 `restoreFloatingWindow()`、`captureScreenRect()` 的 show 恢复处、以及 `mainWindow.on('show')`(托盘显示/对话框恢复)统一调用。
  3. `preload/index.ts`:暴露 `pointer.onSyncCursor(cb)` 订阅 `pointer:sync-cursor`。
- **关键设计**:穿透状态唯一真源仍在渲染层,主进程「重挂」时传入的就是渲染层上次上报的值,不会制造新的失同步;兜底链路(主进程推坐标 + `elementFromPoint`)完全不依赖 forward 转发,即使转发失效也能恢复交互。
- 验证:teacher `tsc --noEmit` 全净(0 错);`electron-vite build` 因本机沙箱禁止子进程管道未能执行,需真机走一遍「聚焦 → 保存 → 取消 → 点浮层」确认。

## 二次修复:聚焦保存后整个浮层「点不动」的真正根因(2026-11-18 下午)
- **用户澄清**:不是「取消对话框后」,而是**聚焦 → 保存之后**,底部工具条(含收起)、侧边栏全部不响应,且**没有弹出原生另存为对话框**也存在。第一版修复没覆盖到。
- **实测手段**(关键):用 `electron-vite dev --remoteDebuggingPort 9333` 起实例 + CDP 驱动 DOM/取坐标 + `mouse_event` 真实点击 + Win32 查窗口 EXSTYLE/WindowFromPoint + 主进程写 `userData/pointer-diag.log` 诊断。
- **逐层排除**:
  1. 窗口样式正常(EXSTYLE 的 WS_EX_TRANSPARENT 已随 setInteractive 正确清除),WindowFromPoint 也命中本窗口 → 不是穿透状态失同步;
  2. 渲染层 mousemove **能收到**(计数器 +3),但 mousedown/pointerdown **完全收不到** → 不是渲染层逻辑/React 问题;
  3. 另起一个普通置顶小窗口做点击探针,同样 `mouse_event` 点击**能收到 2/2** → 不是系统级「吞 mousedown」(uIOhook setMouseConsume 全程未开启,诊断日志无 consume 记录);
  4. 窗口 IsWindowEnabled=True、GetCapture()=0、非 cloaked、且 z-order 在最前 → 不是被禁用/被遮挡。
- **真正根因**:该浮层窗口(transparent + `WS_EX_NOACTIVATE` + `type:'toolbar'` + `focusable:false`)在**「保存」这条链路上**会丢失鼠标按下事件。触发组合是:**真实鼠标点击聚焦层按钮 → 渲染层卸载聚焦层 → 主进程把窗口移出屏幕/隐藏 + 原生对话框/截屏 → 回来后窗口永久收不到 mousedown**(mousemove 正常,所以 hover 高亮还会变,但点了没反应,只能重启)。
  - 对照实验:`spotlight:capture`(移出屏幕→截屏→移回,不弹对话框)后点击**正常**;点「关闭」退出聚焦(不保存)后点击**正常**;只有「保存」路径坏。
  - 原生「另存为」对话框(即使不传 parent)是加重因素之一:取消后同样永久点不动。
- **修复**:
  1. **保存不再使用原生对话框,也不再隐藏/移动窗口**:`spotlight:save-quick` 直接存到 `图片/C30聚焦/聚焦_<时间戳>.png` 并返回路径,渲染层用 4s 自动消失的 toast 提示「已保存:…」。聚焦层在点击保存时已由渲染层卸载、窗口本身透明,所以截屏仍是干净画面,不需要 hide/park。删除了 `spotlight:save`(原生对话框)处理器与 preload 方法,防止再次触发。
  2. **插入白板同款处理**:改为渲染层先 `setActiveTool('select')` + 等两帧卸载聚焦层,再调 `spotlight:capture`;`captureScreenRect` 整个去掉 `hideWindow` 参数与移出屏幕逻辑(调用方保证窗口无装饰),彻底不再有「真实点击后隐藏/移动窗口」的路径。`SpotlightLayer.onCapture` 签名同步简化。
  3. 保留第一版的穿透双保险(唯一真源 `lastStateRef` + 主进程按鼠标位置推送 + `elementFromPoint` 兜底),它保证 hover 判定不依赖 Chromium 的 forward 转发;`mainWindow.on('show')` 里额外把 `applyConsume(false)` 复位。
  4. `userData/pointer-diag.log` 诊断保留(`POINTER_DIAG=0` 可关),记录 set-interactive / consume / save 路径,便于下次定位。
- **验证**(全部真实鼠标点击,scaleFactor 1.5/2 两种显示环境都过):
  - 聚焦 → 放大 → 恢复 → 保存 → toast 显示路径 + 文件真实落盘(1.4MB PNG);
  - 保存后点「收起」→ 工具条折叠成功;展开后点侧边栏「白板」→ 白板正常打开;
  - 聚焦 → 插入白板 → 白板内「关闭」→ 侧边栏「菜单」→ 设置面板打开(整链可点);
  - `tsc --noEmit` 0 错、`electron-vite build` 通过。
- **经验**:
  - 这个项目的透明悬浮窗对「隐藏/移出屏幕 + 原生模态窗口 + 真实点击」的组合非常敏感,任何「隐藏窗口再恢复」的交互都要真机点一遍验证,不能只看状态位。
  - 判断「点不动」要分层:窗口 EXSTYLE → WindowFromPoint → 渲染层 DOM 事件计数器 → 独立窗口探针,逐层排除比猜快得多。
  - `userData/pointer-diag.log`(可用 `POINTER_DIAG=0` 关闭)已保留为常驻诊断,记录 set-interactive/consume/park/restore/save 路径。

## 左右侧边浮层:允许双收起 + 互斥展开 + 位置独立 + 收起态可拖(2026-11-18 晚)
- **用户需求**:①两侧浮层不必强制总有一侧展开,允许**两侧都收起**;但展开时**只能开一个**;②改一侧的高度/位置**不能带动另一侧**,两侧位置各自独立;③**收起后的箭头也要能拖动**。

## 聚焦「插入白板」的图片改为底图(2026-11-18 晚)
- **用户反馈**:聚焦 → 插入白板后,画笔盖不到插入的图片上方(图片盖住了笔迹)。
- **根因**:`Whiteboard.tsx` 里图片是**绝对定位且渲染在 `<canvas>` 之后**,canvas 又是静态(未定位)元素——按 CSS 绘制顺序「定位元素永远画在静态元素之上」,所以图片压在画布和所有笔迹上面。
- **修复**(教师端 + 学生端同改):
  1. 图片移到 `canvas` **之前**,包一层 `position:absolute; inset:0; pointerEvents:none` 的底图层;
  2. 给 `canvas` 加 `position: relative`,让它成为定位元素——两者同为定位元素时按 DOM 顺序绘制,于是「底图在下、canvas 笔迹在上」;
  3. 其余浮层(框选、选择框、弹幕、按钮)仍在 canvas 之后,绘制顺序不受影响。
- **顺带修掉两个连带 bug**:
  1. **教师端看不到自己插入的图片**:服务端 `whiteboard.event` 用 `client.to(roomCode)` 转发,**排除发送者**,所以教师端 emit 的 `image.append` 永远不会回到自己。新增 `WhiteboardHandle.appendImage()`,教师端插入后在本地先追加一份,再广播给学生端(TeacherWorkspace 用 `pendingImage` state + effect 在白板挂载后交给它)。
  2. **快照会把本地底图冲掉**:白板挂载时拉 `whiteboard.state`,若快照先返回(服务端还没收到 `image.append`),`imagesRef.current = snap.images` 会把刚本地插入的底图覆盖掉。改为按 id 合并(保留快照里没有的本地图片)。
- 验证(生产构建 + CDP):插入后 `imgCount=1`、`imgRect=[512,278,1536,835]`、图片层索引 < canvas 索引、`canvas` 计算样式 `position: relative`;用户本人真机确认「画笔可以盖住图片」。

## 白板擦升级:矩形板擦 + 自由擦除 + 高级菜单(清笔迹 / 区域擦除)(2026-11-18 晚)

- **用户需求**:①板擦只在「鼠标按下」时才出现,并且是**矩形**样式;②擦除要能**自由拖动连续擦**(不要一下一下点);③若实现上分步采样,步长要**足够细**,手感像自由擦除;④板擦要有**高级菜单**,含「清笔迹」与「区域擦除」,区域擦除「类似另一种画笔,交集部分就擦掉」。

## 事故:「托盘反复点击 → 内存 100%」实为 lint 进程炸弹(2026-11-18 晚)

- **用户反馈**:托盘反复点击后内存飙到 100%,怀疑托盘点击泄漏。
- **初查(托盘侧)**:教师端 `createTray()` 只建一个 Tray、一个 click 处理器,点击走 `mainWindow.hide()/show()`;
  `show` 事件里 `reapplyPassthrough()` 只发一次 `pointer:sync-cursor` IPC,渲染层 `apply()` 有状态去重。
  **无累积分配、无重复监听、无新增定时器** —— 托盘路径不是泄漏点(代码已核对,未改动)。
- **真正原因(用户提示"进程里有很多 pnpm.exe"后确认)**:`cmd.exe` 5803 个、`pnpm.exe` 5801 个,每秒还在涨。
  调用链是 `pnpm.exe run lint` → `cmd.exe /C pnpm run lint` → 下一级 …… 无限递归;
  源头是根脚本 `pnpm lint` = `turbo run lint`,turbo 逐包调 `pnpm run lint`,本机 Volta + corepack 的 pnpm shim
  在这条链上自我递归(单个包脚本 `tsc --noEmit` 无辜)。这与 CONTRIBUTING 里"turbo lint 本机卡死"的记录同源,
  只是此前只表现为「卡住」,这次被反复触发后放大成进程炸弹。
- **清理踩坑(值得记)**:
  1. `taskkill /PID <root> /T /F` **无效** —— 后代链已经自我复制,杀掉祖先不会让深层的链停止;
  2. **只杀 pnpm 也无效**:链是 pnpm → cmd → pnpm,`cmd` 才是传播节点,杀掉 pnpm 后它的父 cmd
     立刻再拉起一个新的 pnpm,进程数原地不动(实测连杀 5904 个,下一轮又是 5902 个);
  3. 正解:**先杀 cmd、再杀 pnpm**,且用 WQL 服务端过滤(`CommandLine LIKE '%pnpm%lint%'`)而不是把
     1 万多个进程拉回客户端筛;循环到清空,本轮 75 轮清完 1.4 万个进程,内存从吃满回落到 22GB 空闲。
- **修复**:
  1. 根 `package.json`:`"lint": "turbo run lint"` → `"pnpm -r run lint"`(效果等价,不再经过 turbo → pnpm 链);
  2. 新增 `scripts/kill-runaway-lint.ps1`(应急清理,支持 `-DryRun` / `-TimeoutSeconds`,实现即上述"先 cmd 后 pnpm"循环);
  3. `docs/CONTRIBUTING.md` 补充:本机禁用 `turbo run lint`、事故机制、清理命令。
- **验证**:受控跑 `pnpm -r run lint`(带守护:pnpm 进程数超 12 立即杀链)——3 秒完成,5 个包 `tsc --noEmit` 全过,
  守护未触发、结束时 pnpm 子进程为 0;`pnpm lint`(新根脚本)同样通过。
- **结论/教训**:内存 100% 这类"看着像 UI 泄漏"的问题,先看**进程数量**再读代码 —— 本次若只盯托盘,
  会改错地方;另外「祖先杀不掉后代链」是自递归炸弹的通用特征,清理必须从传播节点下手。

## 移除 turbo:多包任务改用 pnpm 原生(2026-11-18 晚)

- **决策依据(实测)**:全量构建约 13 秒(teacher 9.4s / student 2.6s / shared+ui+mdsd tsc 1.0s),
  turbo 的并行与拓扑排序与 `pnpm -r` 完全重合;缓存对最贵的任务实际不生效——`turbo.json` 的
  `outputs` 写的是 `dist/**`、`.next/**`,而 electron-vite 产物在 `out/`、whiteboard-native 在
  `build/Release/`,能命中的只有 1 秒的 tsc 包;远端缓存没配,CI(`build-windows.yml`)也是
  直接用 `pnpm --filter ... build:win`,完全没经过 turbo。结论:**收益上限十几秒,成本是一个原生
  二进制 + daemon + 会炸的调用链**,性价比不成立。
- **改动**:根 `build`/`build:win`/`dev` 换成 `pnpm -r`(`dev` 加 `--parallel`,与 turbo 的并行等价,
  pnpm 的 `-r` 默认就是拓扑序);移除 `turbo` 依赖;删 `turbo.json`、`.turbo/`、`.gitignore` 条目;
  README 与 CONTRIBUTING 同步。
- **顺带发现两处坑**:
  1. 原来的根 `pnpm build` 在本机**本来就是坏的**:`turbo run build` 会跑到
     `apps/whiteboard-native`(`cmake-js compile`),而本机没装 cmake,必挂。该 addon 目前
     没有任何包依赖(`main` 指向的 `build/Release/*.node` 从未生成),属 WIP。故根 `build` 改为
     排除它,另加 `pnpm build:native` 单独构建;
  2. 根 `test` 是空转:`turbo run test` 找不到任何包的 `test` 脚本,跑起来什么都不做。已删除,
     避免把它当安全网(以后加测试时再补 `pnpm -r run test`)。
- **验证**:`pnpm install` 后 turbo 从 node_modules/lockfile 消失,postinstall 原生产物自检通过;
  `pnpm build` 3.2s 退出 0(5/7 包:teacher、student、shared、ui、mdsd 全过);
  `pnpm lint` 6/7 包全过、退出 0。
- **代价**:放弃本地任务缓存(对当前规模≈0 收益)。若将来包数/构建时长上来、或需要 CI 多机共享
  缓存,再引入 turbo 并**同时**修好 `outputs` 与 `env` 声明。

## 浮层功能调整:去拖拽图标 / 任意位置可拖 / 入场动画 / 颜色盘 / 板擦收敛(2026-11-18 晚)
