## M3 架构回顾 + C++ 迁移评估 + 局域网优化(2026-11-17 深夜)
- **架构回顾结论**:数据层(Stroke 纯数据/压感算法/协议)与渲染完全解耦,可无缝迁移 C++;但渲染层未真正抽象(renderStroke 是组件内闭包,未落地文档设计的 Renderer 接口),且存在 O(n²) 全量重发 + 全量重绘两个性能隐患。
- **用户决策**:①先修延迟+抽渲染接口(纯 JS 零新依赖);②局域网采用"双轨自动降级"(优先直连教师,mDNS 失败回退中心服务器)。
- **已落地三项**:
  1. **stroke.live 增量点发送**:LiveStrokeDelta{id,delta,done},教师端 pointermove 只发新增点(sentCountRef 追踪),消除 O(n²) 全量重发;学生端 liveStrokesRef(Map<id,Stroke>) 本地累积 delta。
  2. **抽 Renderer 接口**:新建 components/Renderer.ts,定义 Renderer 接口(render/renderIncremental/renderLive/remove/clear/resize)+ CanvasRenderer 实现(核心 drawStroke 唯一依赖 Canvas API 的地方)。Whiteboard.tsx 改用 rendererRef,未来换 NativeRenderer(C++)只换实现类。
  3. **mDNS 双轨直连**:mdsd 包用 bonjour-service 真实实现(教师端 publish 广播 roomCode/teacherName/host/port,学生端 subscribe 发现)。教师端主进程内嵌 socket.io server(localSessionServer.ts,监听 0 端口+0.0.0.0,复用 NestJS 协议内存版),mDNS 广播;学生端主进程订阅发现+IPC 通知 renderer;双端 renderer 连接逻辑改为"优先直连内嵌 server,connect_error 回退中心 127.0.0.1:3000"。学生端 UI 显示"局域网直连/服务器中继"模式。
- **关键架构决策**:教师端 renderer 也优先连内嵌 server(而非中心服务器),保证教师+学生落在同一套房间状态(否则 roomCode 不互通)。中心服务器仅作降级/云同步。

- **坑**:socket.io 4.8 的 Server.listen 只接受(srv|number, opts?),不接受 callback 和 host;绑定 host 须用 http.createServer()+io.attach()+httpServer.listen(port,host,cb)。已用此方案解决。catch(err) 的 err 在严格模式是 unknown,访问 .message 需 as Error 断言。

## 修复:书写误操作桌面(主进程同步接管) + 笔迹恒宽(2026-11-17 深夜7)
- **用户反馈**:①书写时仍能选中背后文字,且"按下即锁定"方案导致底部工具栏不响应(问题扩大);②笔迹浓度粗细不一致(起笔粗、快速书写细、结尾粗)。
- **问题1根因复盘**:
  - 上一版"按下即锁定"把捕获开关放在**渲染层 onDown/onUp**,依赖异步 IPC + 全局钩子 mouseup,存在竞态:mouseup 丢失时 drawingActive 卡死→set-interactive 被忽略→工具栏永久不响应。
  - uiohook-napi 只监听不拦截(其 addon.c 的 dispatch_proc 未暴露 libuiohook 的 event.reserved 拦截能力),故无法"吞掉"事件。

  - registerPointerControl 的 set-interactive 在 drawingActive 时忽略(防悬停检测覆盖书写接管)。
  - registerAnnotationControl 关闭批注时兜底复位 drawingActive(防卡死)。
  - 原理:书写拖动时窗口不穿透→浏览器收不到 mousemove→无法"拖动框选";抬起恢复穿透→桌面可继续操作。残留:按下那一拍可能透传(单击定位光标),但非"框选拖黑",可接受(近 C30"单点通过")。

  - 根因:strokeWidthFor 有"速度敏感压感"(speed越快越细),教培白板场景下观感不一致,被视为 bug。
  - 修复:packages/shared/src/whiteboard.ts 的 strokeWidthFor 改为**恒定宽度**(speed 入参保留但忽略),brush/pen/pencil 各返回与笔类型匹配的固定系数宽度。两端 Renderer 自动生效(shared 直接消费 src)。

## 修复:按下无法移动鼠标(吞 DRAGGED 冻结光标)+ consume 跟随 hover(2026-11-18 凌晨4)
- **现象**:悬浮栏可点了,但画笔按下左键后鼠标无法移动,松开才能移动。
- **根因**:上一版 C 层吞了 EVENT_MOUSE_DRAGGED。reserved=0x01 的语义是「不调用 CallNextHookEx」,把整个鼠标消息(含移动)都拦下 → 光标本身被冻结。吞掉 move/drag 不仅阻止桌面框选,连光标移动都阻止了。
- **正确认知**:桌面「框选/拖动」的触发条件是「先收到 WM_LBUTTONDOWN 进入按下态,再收到 WM_MOUSEMOVE」。所以**只需吞掉 mousedown**,让桌面收不到「按下」,就不会进入框选态;mousemove 放行后光标正常移动、笔迹正常画。
- **C 层修改(addon.c dispatch_proc)**:只吞 EVENT_MOUSE_PRESSED,放行 DRAGGED/RELEASED;RELEASED 时 `g_consume_mouse=0` 自复位(兜底,不依赖 JS)。
- **JS 主进程重构(核心:consume 必须在按下前就绪)**:
  - 根本时序矛盾:dispatch_proc 在 mousedown 时同步检查 g_consume_mouse,而 JS 只能在 tsfn 异步派发后设置它 → 第一次 mousedown 永远来不及被吞。因此 consume 状态必须由「mousedown 之前的信号」驱动。
  - 方案:consume 跟随「鼠标是否悬停在悬浮栏上」(pointerInteractive,由 usePointerPassthrough 的 hover 检测经 pointer:set-interactive 上报)。主进程在 mousemove(按下前必有)+ pointer:set-interactive 两处持续维护:批注模式下悬停空白区→吞 mousedown,悬停悬浮栏→不吞(悬浮栏可点)。
  - 删除 drawingActive 状态及 mousedown/mouseup 里的 setImmediate setMouseConsume 逻辑(旧「按下才吞」模型废弃)。
  - 新增模块级 applyConsume(on)(带 consumeOn 缓存,幂等),registerGlobalMouseHook/registerPointerControl/registerAnnotationControl 三处统一复用。
  - batch:set-active(true) 时 applyConsume(!pointerInteractive) 预热(切画笔后直接点桌面也能拦);false 时 applyConsume(false) 复位。
- **验证**:教师端 tsc 全净 + electron-vite build 通过(2180 modules);C 层编译通过(仅吞 PRESSED,无 DRAGGED),二进制 00:21 已更新。
- **待真机验证**:①画笔按下后鼠标能正常移动(笔迹跟随);②书写时桌面不框选;③悬浮栏在画笔模式下仍可点(选颜色等);④抬起后桌面恢复可操作。
